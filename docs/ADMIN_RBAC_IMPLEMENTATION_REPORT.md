# Две роли административной панели IANep

Проверка локальной реализации 11 октября 2026 года. Изменения находятся только в рабочем дереве; production, публичные правовые тексты и согласованный договор v2 не менялись.

## Модель доступа

`owner` — существующий главный администратор. `operator` — сотрудник с общей очередью заявок и проектов. Назначений на сотрудников и дополнительных ролей нет. Новые сотрудники создаются только владельцем, открытой регистрации нет. У каждой записи уникальный логин. Блокировка, смена пароля и отзыв сеансов увеличивают `sessionVersion`; каждый запрос с сессией сверяет подпись, срок, ID, логин, роль, активность и версию с записью в БД.

| Маршрут или серверное действие | owner | operator | Клиент / гость |
|---|:---:|:---:|:---:|
| `/admin`, `/admin/briefs/[id]`, просмотр согласия | да | да | нет |
| Изменить рабочий статус заявки, начать проект | да | да | нет |
| Архивировать или восстановить заявку | да | нет | нет |
| `/admin/projects`, `/admin/projects/[id]`, создать клиента и проект | да | да | нет |
| Этапы, версии, результаты, материалы, платежи, обычные изменения проекта | да | да | нет |
| Архивировать/восстановить проект, убрать этап из плана, изменить доступ клиента и отозвать его сеансы | да | нет | нет |
| `/admin/notifications`, собственные уведомления; `/admin/events`, журнал | да | да | нет |
| `/admin/staff`, создание, блокировка, пароль, отзыв сеансов сотрудников | да | нет | нет |
| `/admin/users`, управление клиентскими аккаунтами | да | нет | нет |
| `/admin/system`, глобальные сроки, почта, очистка | да | нет | нет |
| `/admin/privacy-requests`, исполнение запросов об удалении | да | нет | нет |
| `GET/POST /api/admin/backup`, `GET /api/admin/backup/download/[id]` | да | нет | нет |
| `GET /api/files/[id]`, `POST /api/projects/[id]/files` | все проекты | все проекты | только свой проект |
| Client actions: решение по версии, свои материалы, настройки | нет | нет | только свой проект |
| Публичная заявка `/api/brief` | да | да | да, с проверкой формы и согласия |

Проверка роли выполняется в обработчиках и server actions, включая прямой вызов по URL. В приватном хранилище сохраняется проверка принадлежности клиента к проекту; операторы не получают клиентскую сессию. Для опасных страниц чужая роль получает 404, резервные API возвращают 403.

## Миграция и журнал

`20261011120000_admin_roles` добавляет `admin_users.role`, присваивает уже существующим администраторам `owner`, затем убирает значение по умолчанию и ограничивает БД двумя значениями. Это сохраняет пароль и доступ владельца; ранее выданную сессию нужно обновить входом после выкладки. Создание нового администратора без явной роли отклоняется. События управления сотрудниками пишутся с ID владельца, временем и действием. Изменения заявок и проектов сохраняют ID действовавшей учётной записи; новые IP в журнал не добавлены.

## Проверки

- Prisma schema valid; все 20 миграций применились к **изолированной локальной** PostgreSQL 17 без изменения production.
- TypeScript, ESLint, 73 обычных и 49 интеграционных тестов, сборка Next.js 16.3.8 прошли.
- Браузерная проверка: оператор получил 200 для общей страницы проектов, 404 для страниц сотрудников, системы, клиентских аккаунтов и запросов на удаление, 403 для API backup. В его меню видны только рабочие разделы. Владелец открыл страницу сотрудников на desktop и mobile.
- Оптимизация изображения через `/_next/image` вернула 200; `/api/health` вернул 200 на локальном dev-сервере. Production сборка завершилась успешно.

## Что остаётся перед выкладкой

Нужны staging-проверка миграции на копии реальных данных, план восстановления, запуск интеграционных проверок в окружении выкладки и отдельное согласие на production deployment. RBAC ограничивает технический доступ, но не определяет юридические основания обработки данных сотрудниками и тремя возможными Исполнителями.
