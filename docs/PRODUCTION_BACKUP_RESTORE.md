# Production backup и восстановление IANep

Рабочие пути: приложение `/opt/ianep/app`, БД `ianep_prod`, storage `/var/lib/ianep/storage`, серверные наборы `/var/backups/ianep/<UTC timestamp>-<id>`. Дамп БД и архив storage образуют один recovery set. При работающем приложении оба файла не являются атомарным снимком: для строгой согласованности согласуйте короткое окно без записей либо проверенную snapshot-процедуру.

## Политика 1.2

Автоматический backup создаётся **только на VPS**. Таймер `ianep-backup.timer` запускается ежедневно в **02:30 Europe/Berlin** с задержкой до 5 минут (`Persistent=true`), с лимитом выполнения 50 минут, отдельно от maintenance в 03:30. После полного создания и проверки нового серверного набора сохраняются ровно **две последние успешные копии**: новая и предыдущая. Неуспешная или незавершённая попытка не запускает очистку успешных наборов. Если исторически есть больше двух успешных наборов, следующий успешный запуск приводит их к двум. Никакого автоматического offsite нет.

Кнопка Admin «Создать резервную копию» предлагает «На сервере» и «Скачать на устройство». Серверный вариант проходит тот же pipeline и retention. Вариант скачивания создаёт отдельный проверенный временный архив в `/var/backups/ianep/exports/`, доступный только администратору, начавшему операцию в текущей версии сессии. Ссылка действует до часа; временные файлы удаляются после выдачи либо по TTL через cleanup timer каждые 15 минут. Браузер сохраняет файл по своим настройкам или через Save As; приложение не пишет в файловую систему устройства и не выбирает папку программно. Download не меняет две постоянные копии.

Архив содержит только `database.dump`, `storage.tar.gz`, `SHA256SUMS`, `manifest.json`. Секреты, `.env.local`, конфигурация приложения и ключи не включаются. Храните скачанный архив как конфиденциальный: он содержит данные клиентов.

## Установка на VPS (отдельный будущий шаг, сейчас production не меняется)

Создайте `/var/backups/ianep` с владельцем `ianep:ianep` и правами `0700`. Пользователь приложения должен читать storage, запускать `pg_dump`, `pg_restore`, `tar` и подключаться к БД для чтения. Не запускайте приложение от root и не выдавайте широкий `sudo`. Установите `deploy/systemd/ianep-backup.service` и `.timer`, а также `ianep-backup-cleanup.service` и `.timer`, убедитесь, что `/opt/ianep/app/.env.local` доступен только пользователю приложения, затем включите оба timer. Оба запуска (timer и Admin) используют атомарную блокировку `.running` в backup root. Если процесс аварийно завершился и блокировка осталась, оператор проверяет состояние и снимает её вручную после исключения действующего запуска. Web-приложение должно работать постоянным процессом на VPS и иметь доступ к этому каталогу.

Проверка перед фиксацией success: `pg_restore --list`, `tar -tzf`, повторный SHA-256 обеих частей. Только после этого записывается manifest со статусом success и выполняется prune. Наборы сортируются по проверенной паре имени и временной метки manifest; удаление ограничено непосредственными каталогами внутри backup root. Для download используется потоковая передача, `Content-Disposition: attachment` и `Cache-Control: no-store`.

## Проверка восстановления

Используйте отдельный PostgreSQL и пустую БД, например `ianep_restore_drill_<stamp>`; никогда не направляйте команду на `ianep_prod`. Если проверка выполняется на том же VPS, учитывайте нагрузку и удаляйте только созданную тестовую БД после проверки.

```sh
sudo -u postgres createdb ianep_restore_drill_<stamp>
sudo -u postgres pg_restore --no-owner --no-acl -d ianep_restore_drill_<stamp> < database.dump
sudo -u postgres psql -d ianep_restore_drill_<stamp> -Atc "SELECT count(*) FROM information_schema.tables WHERE table_schema='public' AND table_type='BASE TABLE'"
sudo -u postgres psql -d ianep_restore_drill_<stamp> -Atc 'SELECT count(*), count(*) FILTER (WHERE finished_at IS NULL AND rolled_back_at IS NULL) FROM public._prisma_migrations'
```

Сверьте историю миграций с релизом, наличие ключевых таблиц и агрегированные счётчики строк. Не выводите персональные данные. До распаковки проверьте список архива на абсолютные пути и `..`; распаковывайте только в пустую disposable-папку, затем проверьте число файлов и общий размер. Не копируйте тестовые данные обратно в production.

## Восстановление после аварии

1. Зафиксируйте инцидент, остановите новые записи и выберите проверенный единый набор БД + storage. Сохраните текущие данные и конфигурацию для анализа.
2. Подготовьте новый/пустой PostgreSQL и отдельный каталог storage. Сохраните необходимые секреты в защищённом хранилище; не включайте их в backup или Git.
3. Проверьте SHA-256, список дампа и архив; восстановите БД и storage в новые места.
4. Сверьте миграции, ключевые таблицы, счётчики и целостность storage. Применяйте только миграции, ожидаемые для выбранного релиза.
5. Настройте приложение на восстановленные ресурсы, запустите сервисы, проверьте `/api/health`, private-file доступ и ownership. После этого возобновите timer и трафик по cutover-плану.

Никогда не восстанавливайте поверх живой БД или storage без явного maintenance/cutover-плана. Не перезапускайте production-сервисы ради учебной проверки.
